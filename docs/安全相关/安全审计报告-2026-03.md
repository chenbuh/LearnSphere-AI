## V9【严重】生产库导出文件已推送到公开远端仓库

### 影响

整个生产数据库导出（含全部用户邮箱、BCrypt 口令哈希、VIP 等级、积分、订单记录，以及 admin 表口令哈希）已随初始化提交进入 Git 历史，并推送到两个公开远端：

```

```

## V1【严重】默认管理员凭证可从仓库直接推出

### 影响

`admin-init.sql` 内置默认管理员，口令明文写在注释里，且代码未强制首登改密。任何拿到仓库或该 SQL 文件的人可直接登录后台。

### 证据

`backend/src/main/resources/admin-init.sql:19-22`：

```sql
-- 账号：admin
-- 密码：admin123（首次部署后请立即修改）
INSERT INTO `admin` (`username`, `password`, `salt`, `nickname`, `status`)
VALUES ('admin', '$2a$10$59kBdletb8Z5J2vbaoAK8.WR3owh7yfh.6mGk8.TLQa.yY6c5pryW', '', '超级管理员', 1)
```

`backend/src/main/java/com/learnsphere/controller/AdminAuthController.java:67-73`：

```java
if (admin == null || !passwordMatches(password, admin.getPassword())) {
    return Result.error("账号或密码错误");
}
if (admin.getStatus() == null || admin.getStatus() != 1) {
    return Result.error("账号已被禁用");
}
```

登录流程无「首次登录强制改密」、无失败锁定计数。

### 复现步骤

1. 编译并运行验证程序（脚本见 `.ig5-audit/evidence/BcryptCheck.java`）：

   ```java
   import cn.hutool.crypto.digest.BCrypt;

   public class BcryptCheck {
       public static void main(String[] args) {
           String hash = "$2a$10$59kBdletb8Z5J2vbaoAK8.WR3owh7yfh.6mGk8.TLQa.yY6c5pryW";
           System.out.println(BCrypt.checkpw("admin123", hash));
       }
   }
   ```

2. 使用项目本地依赖编译执行：

   ```powershell
   $hutool = "$env:USERPROFILE\.m2\repository\cn\hutool\hutool-all\5.8.36\hutool-all-5.8.36.jar"
   javac -cp $hutool -d out BcryptCheck.java
   java -cp "out;$hutool" BcryptCheck
   # 输出：true
   ```

3. 确认口令匹配后，直接登录后台：

   ```http
   POST /api/admin/auth/login
   Content-Type: application/json

   {"username":"admin","password":"admin123"}
   ```

   预期返回 `Result.success` 并携带 `satoken`，即成功进入后台。

### 实测结果

```

no           admin
no           123456
no           admin@123
no           password
```

### 修复

- 删除 `admin-init.sql` 中的默认管理员 INSERT 语句。
- 改为首次启动生成随机强口令并打印到控制台（仅一次），或由环境变量 `ADMIN_INIT_PASSWORD` 注入，缺省则跳过创建。
- 在 `admin` 表增加 `must_change_password` 字段，登录后强制改密。
- `AdminAuthController` 增加连续失败计数与锁定（现有 `@RateLimit` 仅限流，不锁定）。

## V2【严重】生产库内 admin 口令已爆破还原

### 影响

生产库 dump 内 `admin` 表使用**无盐 MD5 + 固定盐**（非代码中声明的 BCrypt），口令可离线秒破。破出的明文同时是数据库口令与加密脚本示例值，形成「一处破、全线通」。

### 证据

`backend/learnsphere_ai_production.sql` 中 admin 表数据：

```sql
INSERT INTO `admin` VALUES
(1,'chen','<REDACTED-MD5>','<REDACTED-SALT>',
   '?,1,0,'2026-01-12 00:37:12','2026-01-12 00:37:12');
```

对比 `AdminAuthController.java:100-103`，现版本仅接受 BCrypt：

```java
private boolean passwordMatches(String rawPassword, String encodedPassword) {
    if (encodedPassword == null || !encodedPassword.startsWith("$2")) {
        return false;
    }
    ...
}
```

说明该 dump 来自**旧版弱哈希实现**，字段 `salt` 存放的是明文固定盐 `<REDACTED-SALT>`。

### 复现步骤

1. 运行 MD5 复现程序（脚本见 `.ig5-audit/evidence/Md5Crack.java`）：

   ```java
   import java.security.MessageDigest;

   public class Md5Crack {
       public static void main(String[] args) throws Exception {
           String target = "<REDACTED-MD5>";
           String salt = "<REDACTED-SALT>";
           String plain = "<REDACTED-DB-PASSWORD>";
           MessageDigest md = MessageDigest.getInstance("MD5");
           byte[] d = md.digest((plain + salt).getBytes("UTF-8"));
           StringBuilder sb = new StringBuilder();
           for (byte b : d) sb.append(String.format("%02x", b));
           System.out.println(sb.toString().equalsIgnoreCase(target)); // true
       }
   }
   ```

2. 执行：

   ```powershell
   javac -d out Md5Crack.java
   java -cp out Md5Crack
   ```

3. 或直接命令行验证盐拼接规则：

   ```bash
   echo -n "<REDACTED-DB-PASSWORD><REDACTED-SALT>" | md5sum
   # <REDACTED-MD5>
   ```

### 实测结果

```
*** MATCH ***
plain  = <REDACTED-DB-PASSWORD>
salt   = <REDACTED-SALT>
input  = "<REDACTED-DB-PASSWORD>" + "<REDACTED-SALT>"
MD5    = <REDACTED-MD5>
```

**同一口令 `<REDACTED-DB-PASSWORD>` 出现在三个位置**：

| 位置 | 内容 |
|---|---|
| `application-secret.properties:12` | `spring.datasource.password=<REDACTED-DB-PASSWORD>`（明文） |
| `encrypt-config.ps1:18` | `"数据库密码" = "<REDACTED-DB-PASSWORD>"`（明文） |
| `learnsphere_ai_production.sql` admin 行 | MD5 破出 `<REDACTED-DB-PASSWORD>` |

### 修复

- 立即轮换该口令；确认生产环境已运行新版 BCrypt 代码（`passwordMatches` 已拒绝旧哈希，但旧记录需重置）。
- 删除 `admin.salt` 列（BCrypt 自带盐）。
- 口令策略：长度 ≥ 12、禁止与库名/用户名/项目名相关、接入弱口令黑名单。
- 数据库、后台、其他服务使用**不同**口令。

## V3【严重】Jasypt 弱算法 + 硬编码密钥 + 假加密脚本

### 影响

配置中的「加密」全部可逆还原。密钥硬编码在源码，密文与密钥同处一个仓库，加密等于编码。

### 证据

**1. 弱算法配置** —— `backend/src/main/resources/application.yml:73-76`：

```yaml
jasypt:
  encryptor:
    algorithm: PBEWithMD5AndDES
    iv-generator-classname: org.jasypt.iv.NoIvGenerator
```

`PBEWithMD5AndDES` 为 DES（56 位密钥）+ MD5 派生，且 `NoIvGenerator` 无初始向量，均属已淘汰算法。

**2. 硬编码密钥** —— `backend/src/main/java/com/learnsphere/utils/JasyptEncryptUtil.java:21`：

```java
private static final String DEFAULT_PASSWORD = "<REDACTED-JASYPT-KEY>";
```

`backend/encrypt-config.ps1:10-14` 同样回退到该密钥。

**3. 假加密脚本** —— `backend/encrypt-config.ps1:30-35`：

```powershell
$bytes = [System.Text.Encoding]::UTF8.GetBytes($plainText)
$encrypted = [Convert]::ToBase64String($bytes)   # 仅 Base64，无任何加密
Write-Host "  密文: ENC($encrypted)"
```

**4. 密文与密钥同仓库** —— `application-secret.properties:16`：

```properties
ai.api-key=ENC(K+73iSEfOLfrEMWPy50xvw3vjlzHNoTXHW8uDUbRj22lOxylGk8bRqfwfmy58qWJ)
```

### 复现步骤

1. 使用项目自带工具类解密（脚本见 `.ig5-audit/evidence/`）：

   ```powershell
   $jasypt = "$env:USERPROFILE\.m2\repository\org\jasypt\jasypt\1.9.3\jasypt-1.9.3.jar"
   # 复制项目 JasyptEncryptUtil.java 后编译
   javac -cp $jasypt -d out JasyptEncryptUtil.java Dec.java
   java -cp "out;$jasypt" Dec "K+73iSEfOLfrEMWPy50xvw3vjlzHNoTXHW8uDUbRj22lOxylGk8bRqfwfmy58qWJ"
   ```

2. 其中 `Dec.java` 内容：

   ```java
   public class Dec {
       public static void main(String[] a) {
           String pw = "<REDACTED-JASYPT-KEY>";
           System.out.println(com.learnsphere.utils.JasyptEncryptUtil.decrypt(a[0], pw));
       }
   }
   ```

3. 若密钥非默认值，可离线爆破（算法弱、密钥为可猜短语）：

   ```bash
   # 使用 jasypt 命令行工具或自写字典程序遍历
   java -cp jasypt-1.9.3.jar org.jasypt.intf.cli.JasyptPBEStringDecryptionCLI \
        input="K+73iS..." password="候选密钥" algorithm=PBEWithMD5AndDES
   ```

### 实测结果

```
PLAINTEXT=[sk-8b5df7e3d85442fd8e4ddb7c5204da48]
```

与 `backend/encrypt-config.ps1:19` 中硬编码的 `AI API Key = "sk-8b5df7e3d85442fd8e4ddb7c5204da48"` **完全一致** —— 证实「加密」未提供任何保护。

### 修复

- 升级算法为 `PBEWITHHMACSHA512ANDAES_256`，并配置 `RandomIvGenerator`：
  ```yaml
  jasypt:
    encryptor:
      algorithm: PBEWITHHMACSHA512ANDAES_256
      iv-generator-classname: org.jasypt.iv.RandomIvGenerator
      salt-generator-classname: org.jasypt.salt.RandomSaltGenerator
      key-obtention-iterations: 100000
  ```
- 加密密钥仅从环境变量 `JASYPT_PASSWORD` 注入，删除代码与脚本中的默认值；密钥缺失时**启动失败**而非回退。
- 废弃 `encrypt-config.ps1` 的 Base64 伪加密，改用 jasypt 官方 CLI 或启动时加密。
- 轮换已泄露的 AI API Key，并重新用新算法加密。
- 历史密文需重新加密（算法变更后旧密文不可解）。

## V5【高危】后台鉴权为单点 URL 前缀判断

### 影响

后台接口的 admin 校验依赖 `SaTokenConfig` 中的 URL 前缀字符串判断，而非注解。20 个 `Admin*Controller` 中仅 **2 个**带类级 `@SaCheckRole("admin")`，其余 18 个完全依赖该单点判断。任何路径前缀变化（重命名、路径拼接、`//`、大小写、新增非 `/api/admin/` 前缀的后台控制器）都会静默丢失 admin 校验。

### 证据

`backend/src/main/java/com/learnsphere/config/SaTokenConfig.java:130-135`：

```java
static boolean requiresAdminAccess(String path) {
    return path != null
            && ((path.startsWith("/api/admin/") && !path.startsWith("/api/admin/auth/"))
                    || path.startsWith("/api/actuator/")
                    || path.startsWith("/api/diagnostic/"));
}
```

**补充验证（字节码级）**：为排除「注解是否真的生效」这一前提，已反编译项目实际依赖 `sa-token 1.37.0`（`backend/pom.xml:30`）的 `SaInterceptor`，从字节码确认：

```
void <init>_void(SaInterceptor this) {
    (*this-><init>)(this);
    *this->isAnnotation = true;      ← 两个构造函数均默认置为 true
    ...
}
```

```c
boolean preHandle(...) {
    if (*this->isAnnotation != false) {                  // 默认成立
        if (instanceof(param3, HandlerMethod)) {
            if (method.hasAnnotation(SaIgnore.class)) return true;
            SaStrategy.checkMethodAnnotation.accept(method);   // ① 注解鉴权先执行
        }
    }
    this->auth.run(handler);                                    // ② 自定义 auth 后执行
    return true;
}
```

**结论**：`@SaCheckRole` 在 1.37.0 中**默认生效**，且执行顺序先于 `SaTokenConfig` 里的自定义 `auth`（含 URL 前缀判断）。因此：

- 已挂注解的方法（如 `AdminAITutorController` 的 10 个方法）受注解保护；
- **未挂注解的控制器与方法，注解层直接跳过，仅由 `requiresAdminAccess` 的字符串前缀判断兜底** —— 本风险项成立。

1. 枚举全部后台控制器与其鉴权方式（该方法识别「无注解兜底」的高风险面）：

## V6【中危】MFA 可被无限重置导致账号接管

### 影响

已绑定 MFA 的账号可被重复调用 `/mfa/setup` 生成新密钥，并通过 `/mfa/bind` 直接覆写数据库中的 `mfa_secret`，**无需验证旧密钥**。攻击者一旦获得有效会话（XSS、token 泄露、共享设备），即可把受害者的 MFA 替换为自己的，完成账号接管。

### 证据

`backend/src/main/java/com/learnsphere/controller/SecurityController.java:37-49`：

```java
@GetMapping("/mfa/setup")
public Result<Map<String, String>> setupMfa() {
    Long userId = StpUtil.getLoginIdAsLong();
    User user = userService.getById(userId);
    String secret = MfaUtil.generateSecret();
    String qrCodeUrl = MfaUtil.getOtpAuthUrl(user.getUsername(), secret);
    ...
}
```

未检查 `user.getMfaEnabled()`，已绑定用户亦可重新获取新 secret。

`:56-71`：

```java
@PostMapping("/mfa/bind")
public Result<Void> bindMfa(@RequestBody Map<String, String> body) {
    String secret = body.get("secret");
    String code = body.get("code");
    if (!MfaUtil.verifyCode(secret, code)) {
        return Result.error("验证码校验失败，请重试");
    }
    ...
    user.setMfaSecret(secret);
    user.setMfaEnabled(1);
    userService.updateById(user);
```

仅校验「新 secret 能生成正确 TOTP」，未要求旧 secret 或账号口令。

### 复现步骤

1. 以受害者账号登录，获取 `satoken`。
2. 重新初始化 MFA：
   ```http
   GET /api/security/mfa/setup
   Cookie: satoken=<受害者的 token>
   ```
   返回新的 `secret` 与 `qrCodeUrl`（即使账号已绑定 MFA）。
3. 使用新 secret 生成 TOTP 并绑定：
   ```http
   POST /api/security/mfa/bind
   Cookie: satoken=<受害者的 token>

   {"secret":"<第2步返回的 secret>","code":"<当前 TOTP>"}
   ```
4. 结果：`user.mfa_secret` 被覆写为新值，受害者原验证器失效，攻击者掌握唯一 MFA。

### 修复

- `setupMfa` 增加已绑定检查：若 `mfaEnabled == 1`，要求先通过旧 MFA 或账号口令验证。
- `bindMfa` 增加二次认证：重新输入账号口令，或提供旧 MFA 验证码。
- 引入「MFA 重绑」独立流程并记录安全日志、发送邮件通知。
- `unlock` 接口同理，考虑加 `@RateLimit` 防止验证码遍历。

## V7【中危】未捕获异常与解析风险

### 影响

白名单路径上的接口在未登录时抛出未捕获异常；另有未经保护的字符串转数字解析。虽被全局异常处理器兜住（返回 401/500），但会产生异常日志噪音，且 500 分支依赖的处理器一旦被修改即可能泄露堆栈。

### 证据

**1. `AdminAuthController.java:152-158`** —— 该接口在鉴权白名单内（`SaTokenConfig.java:62-64` 排除 `/api/admin/auth/**`），但方法体直接调用会在未登录时抛异常的方法：

```java

public Result<?> learnerSession() {
    String loginId = String.valueOf(StpUtil.getLoginId());   // 未登录时抛 NotLoginException
    if (!loginId.startsWith("admin:")) {
        return Result.error("仅管理员账号可使用");
    }
```

**2. `SecurityController.java:104-112`** —— `Integer.parseInt` 无异常保护：

```java
Object violations = redisTemplate.opsForValue().get(key);
Map<String, Object> result = new HashMap<>();
result.put("violations", violations == null ? 0 : Integer.parseInt(violations.toString()));
result.put("isLocked", violations != null && Integer.parseInt(violations.toString()) >= 10);
```

若 Redis 中该键被写入非数字内容，将抛出 `NumberFormatException`。

**3. `GlobalExceptionHandler.java:68-72`** —— 兜底处理器返回固定文案，未泄露堆栈（此点实现正确）：

```java
@ExceptionHandler(Exception.class)
public Result<?> handleException(Exception e) {
    log.error("系统异常: ", e);
    return Result.error("系统异常，请联系管理员");
}
```

### 复现步骤

1. 不带任何 token 调用白名单内的 learner-session：
   ```http
   POST /api/admin/auth/learner-session
   ```
   观察响应与日志：请求进入该方法体，`StpUtil.getLoginId()` 抛 `NotLoginException`，由全局处理器转为 401。
2. 检查应用日志确认异常抛出路径：
   ```bash
   grep -n "未登录异常" runtime.log
   ```
3. 若可写入 Redis（如通过其他缺陷），构造非数字值后访问风险状态接口：
   ```http
   GET /api/security/risk-status
   ```
   触发 `NumberFormatException`。

### 修复

- 统一改用 `StpUtil.getLoginIdDefaultNull()` 并显式判空返回 401：
  ```java
  Object loginId = StpUtil.getLoginIdDefaultNull();
  if (loginId == null) {
      return Result.error(401, "未登录");
  }
  ```
- 解析封装为安全方法：
  ```java
  private int readInt(Object value, int fallback) {
      if (value == null) return fallback;
      try { return Integer.parseInt(value.toString().trim()); }
      catch (NumberFormatException e) { return fallback; }
  }
  ```
- 保持 `GlobalExceptionHandler` 不返回堆栈（现状正确），并为其补充单元测试。

```java
                + "&out_trade_no=" + URLEncoder.encode(order.getOutTradeNo(), StandardCharsets.UTF_8);
```

### 复现步骤

1. 配置易支付（`epay.enabled=true`、`epay.key=...`）并创建一笔 `PENDING` 订单。

- 若网关支持，改为 POST 提交参数（避免 URL 落日志）。
- 无法改为 POST 时，出站请求日志必须脱敏 `key` 参数：

  ```java
  private static String redact(String url) {
  ```

- 在网关侧将商户密钥作为长期凭证定期轮换，并限制查单接口来源 IP。
- 清理历史日志中可能已落盘的密钥，并轮换该密钥。

## V12【中危】TOTP 实现的三项偏差

### 影响

`MfaUtil` 的三处实现偏离 RFC 4226/6238 与安全惯例。

### 证据与逐项分析

**① 密钥长度低于规范下限** —— `MfaUtil.java:26`（修复前）：

```java
byte[] buffer = new byte[10];                          // 10 字节 = 80 位
RandomUtil.getSecureRandom().nextBytes(buffer);
```

RFC 4226 要求共享密钥**至少 128 位**，Google Authenticator 默认 160 位（20 字节）。80 位低于下限。

**② 验证码比较非常量时间** —— `MfaUtil.java:62`（修复前）：

```java
return generatedCode.equals(code);                     // 短路比较
```

对比项目自身在 `EpaySigner.java:34` 的正确做法：

```java
return MessageDigest.isEqual(sign.toLowerCase().getBytes(StandardCharsets.UTF_8),
        sign(params, key).getBytes(StandardCharsets.UTF_8));
```

同一项目内两套标准，MFA 侧反而弱于支付侧。

**③ 无防重放** —— `MfaUtil.java:34-42` 仅判断时间窗有效性，不记录已使用的计数器：

```java
public static boolean verifyCode(String secret, String code) {
    long counter = Instant.now().getEpochSecond() / TIME_STEP;
    return checkCode(secret, code, counter - 1) ||
            checkCode(secret, code, counter) ||
            checkCode(secret, code, counter + 1);
}
```

由于接受前后各一个窗口，同一个 6 位码在约 **90 秒**窗口内可被重复使用，影响：

- `/api/security/unlock` —— 一次验证码可反复解除风险锁定
- `/api/security/mfa/unbind` —— 一次验证码可反复解绑
- `/api/security/mfa/bind` —— 绑定阶段的验证码可被复用

### 复现步骤

1. 生成密钥并观察长度：
   ```java
   String s = MfaUtil.generateSecret();
   System.out.println(s.length());   // 修复前 Base32(10字节)=16 字符；修复后 32 字符
   ```
2. 在同一时间窗内重复调用 `verifyCode(secret, code)` 并传入同一验证码，均返回 `true`（无重放保护）。
3. 比较方式可通过反编译确认使用 `String.equals` 而非 `MessageDigest.isEqual`。

### 修复

**① 密钥长度**：

```java
/** 密钥字节数：160 位，符合 RFC 4226 建议且与主流验证器一致 */
private static final int SECRET_BYTES = 20;

public static String generateSecret() {
    byte[] buffer = new byte[SECRET_BYTES];
    RandomUtil.getSecureRandom().nextBytes(buffer);
    return Base32.encode(buffer).toUpperCase();
}
```

**② 常量时间比较**：

```java
return MessageDigest.isEqual(
        generatedCode.getBytes(StandardCharsets.UTF_8),
        code.trim().getBytes(StandardCharsets.UTF_8));
```

**③ 防重放**（已实施）：新增 `verifyCodeWithStep()` 返回命中的时间步，配合 Redis 一次性消费键：

```java
// MfaUtil：返回命中的时间步，失败返回 -1
public static long verifyCodeWithStep(String secret, String code)

// 重放键：mfa:used:{scope}:{subjectId}:{timeStep}
public static String replayKey(String scope, Object subjectId, long timeStep)
public static long replayKeyTtlSeconds()   // 120 秒，覆盖 3 个窗口
```

`SecurityController` 新增统一校验方法，**顺序严格为「校验成功 → 检查重放 → 标记已使用」**：

```java
private boolean verifyAndConsumeMfa(String scope, Object subjectId, String secret, String code) {
    if (code == null || code.isBlank()) return false;

    long timeStep = MfaUtil.verifyCodeWithStep(secret, code);
    if (timeStep < 0) return false;              // 校验失败：绝不占位

    String key = MfaUtil.replayKey(scope, subjectId, timeStep);
    Boolean firstUse = redisTemplate.opsForValue().setIfAbsent(key, "1");   // 原子判重
    if (!Boolean.TRUE.equals(firstUse)) {
        log.warn("检测到 MFA 验证码重放：scope={}, subject={}, timeStep={}", scope, subjectId, timeStep);
        return false;
    }
    redisTemplate.expire(key, Duration.ofSeconds(MfaUtil.replayKeyTtlSeconds()));
    return true;
}
```

**为什么顺序不能颠倒**：若在校验通过前就占位，攻击者可用任意错误验证码把窗口占掉，导致合法用户无法使用（拒绝服务）。因此失败路径必须直接返回、不触碰 Redis。

三个调用点全部改接：`/mfa/bind`（scope=`bind`）、`/mfa/unbind`（scope=`unbind`，仅验证码路径）、`/unlock`（scope=`unlock`）。

### 修复验证（已实测）

使用**独立实现的 TOTP** 交叉校验被测代码，避免「自己验自己」：


## V14【中危】登录/注册被排除出防爬拦截器，双层防护降为单层

### 影响

`WebConfig` 的拦截器注册将 `/api/auth/login` 与 `/api/auth/register` 排除在 `AntiCrawlerInterceptor` 之外，使这两条最敏感路径**只剩下 `@RateLimit(limitType = IP)` 一层防护**。

V13 修复后 `@RateLimit` 已可信，因此该问题**不再可直接利用**；但「双层防护降为单层」本身是纵深防御缺陷，单点失效即无兜底。

### 证据

修复前 `backend/src/main/java/com/learnsphere/config/WebConfig.java:51-59`：

```java

    registry.addInterceptor(antiCrawlerInterceptor)
            .addPathPatterns("/api/**")

}
```

对应地，`AuthController` 仅有单层 `@RateLimit`：

```java

```

### 复现步骤

1. 修复前，向登录接口发送超过 60 次/分钟的请求：

2. 若同时伪造 `X-Forwarded-For`（修复前），两层均可绕过。

### 修复

移除两条排除项，使登录与注册同时受两层约束：

```java
        .excludePathPatterns(

```

选择保留 `/api/health` 排除的理由：其为探活接口，不应消耗限流额度，且不涉及认证与状态变更。

**阈值合理性**：全局阈值为 60 次/分钟/IP，对正常用户的登录与注册操作绰绰有余（人类不可能一分钟登录 60 次），但对自动化爆破构成有效遏制。

## V13【严重】客户端 IP 可伪造，导致全站限流与风控失效

### 影响

项目中存在 **4 处独立的客户端 IP 解析实现**，全部无条件信任客户端可设置的请求头，且取代理链中的**第一个**地址——而该位置正是客户端可任意伪造的值。

攻击者只需发送 `X-Forwarded-For: <任意 IP>`，即可让每次请求呈现为不同来源，直接导致：

- 绕过全部 `@RateLimit(limitType = IP)` 限流；
- 绕过 `AntiCrawlerInterceptor` 的请求计数与 IP 黑名单；
- 污染 `user_log` / `security_log` 的来源 IP 与地理位置。

### 证据

**4 处实现（修复前）**：

| 文件 | 行 | 信任的头 | 取值方式 |
|---|---|---|---|
| `IpUtils.java` | 41-61 | `X-Forwarded-For`、`Proxy-Client-IP`、`WL-Proxy-Client-IP`、`HTTP_CLIENT_IP`、`HTTP_X_FORWARDED_FOR` | `split(",")[0]`（第一个） |
| `IpUtil.java` | 18-28 | `X-Real-IP`、`X-Forwarded-For` | `substring(0, index)`（第一个） |
| `AntiCrawlerInterceptor.java` | 95-104 | `X-Real-IP`、`X-Forwarded-For` | 第一个 |
| `RateLimitAspect.java` | 91-100 | `x-forwarded-for`、`Proxy-Client-IP`、`WL-Proxy-Client-IP` | 整串 |

`IpUtils.java:41-61`（修复前）：

```java
public static String resolve(HttpServletRequest request) {
    String remoteAddr = normalize(request.getRemoteAddr());

    // 未配置可信代理时，只认 TCP 对端地址，忽略全部转发头
    if (trustedProxyCount <= 0) {
        return remoteAddr;
    }

    String forwarded = request.getHeader("X-Forwarded-For");
    if (forwarded == null || forwarded.isBlank()) {
        return remoteAddr;
    }

    String[] chain = forwarded.split(",");
    // XFF 语义：[客户端, 代理1, ..., 代理N]，末尾 N 项由可信代理写入
    // 真实客户端位于从右往左第 trustedProxyCount 个位置
    int index = chain.length - trustedProxyCount;
    if (index < 0 || index >= chain.length) {
        return remoteAddr;                 // 链长度不足，不可信
    }

    String candidate = normalize(chain[index]);
    return isValidIp(candidate) ? candidate : remoteAddr;   // 格式校验
}
```

**4 处调用点全部改接**，并新增配置类 `ClientIpConfig` 读取 `app.security.trusted-proxy-count`：


## V20【严重】AI 配额扣减竞态（TOCTOU），可无限白嫖付费接口

### 影响

`VipCheckAspect` 的每日配额扣减是**非原子的「读-判-写」三步**。并发请求会读到同一个 `usedCount`，各自加 1 后先后写回相同值，**后写覆盖先写**，导致 N 个并发请求只扣 1 次配额。

攻击者只需并发调用 AI 接口，即可把每日 15 次配额变成近乎无限次，**直接造成上游 AI 服务的计费损失**；而 Redis 中的计数显示正常（如 1/15），运营侧**难以察觉**。

### 证据

修复前 `VipCheckAspect.java:84-122`：

```java
String usedCountStr = redisTemplate.opsForValue().get(quotaKey);   // ① 读（非原子）
int usedCount = usedCountStr != null ? Integer.parseInt(usedCountStr) : 0;
...
if (usedCount >= dailyQuota) {                                     // ② 判
    throw new QuotaExceededException(...);
}
int newCount = usedCount + quotaCost;                              // ③ 本地相加
redisTemplate.opsForValue().set(quotaKey, String.valueOf(newCount), 1, TimeUnit.DAYS);  // ④ 覆盖写
```

**同项目内的正确做法**（`RateLimitAspect:42`）使用原子自增：

```java
Long currentCount = redisTemplate.opsForValue().increment(finalKey);
```

**同一个项目里，限流做对了，配额做错了。**

### 字节码验证（IG5 反编译 `VipCheckAspect.checkVip`）

反编译 `checkVip`（`0x10000`，738 字节）后确认扣减路径：

```
:148  pOVar4 = (*pVVar14->get)(pVVar14, pSVar6);          ← 读
:154  iVar24 = (*Integer_parseInt)(pSVar11);              ← 解析
      ...                                                 ← 判（超限抛异常）
:304  *puVar16 = *puVar16 + puVar16[-1];                  ← 本地相加
:319  (*((void *)*puVar16)->set)(...)                     ← set 覆盖写
```

关键证据：`:319` 调用的是 **`set`**，不是 `increment`。分类为**观察到的实现方式**，TCCTOU 可被利用性由下述并发实验佐证。

### 复现步骤

`.ig5-audit/evidence/QuotaRaceTest.java` —— 用内存模型模拟 Redis 语义，对比两种写法在 50 并发下的行为：

```
================ 配额扣减竞态验证 ================
并发线程: 50   每日配额: 15   单次消耗: 1

【修复前】get → 判 → set（非原子）
  放行请求数: 50   (配额上限 15)
  最终计数值: 1
  => 实际放行 50 次，超出配额 35 次
  => !! 配额被突破，存在丢失更新

【修复后】increment 原子自增 + 超限回滚
  放行请求数: 15
  最终计数值: 15
  => OK 严格等于配额，无超额
```

**修复前：50 个并发请求全部放行，计数器只涨到 1。** 并发越高，超额越严重。

### 修复

改用 Redis 原子自增，超限则回滚：

```java
int quotaCost = getQuotaCostForFeature(requireVip.feature(), requireVip.quotaCost());
if (quotaCost < 0) {
    // 配额消耗为负会导致「越用越多」，是配置错误，直接拒绝
    throw new BusinessException(500, "配额配置异常，请联系管理员");
}

Long newCount = redisTemplate.opsForValue().increment(quotaKey, quotaCost);

if (newCount == null) {
    // Redis 异常时按保守策略拒绝（宁可少放行，不可超发）
    throw new BusinessException(500, "配额服务暂时不可用，请稍后重试");
}

if (newCount == quotaCost) {
    redisTemplate.expire(quotaKey, Duration.ofDays(1));   // 当日首次递增时补设过期
}

if (newCount > dailyQuota) {
    // 超限：回滚本次预扣，避免计数被超额请求推高
    Long rolledBack = redisTemplate.opsForValue().decrement(quotaKey, quotaCost);
    if (rolledBack != null && rolledBack <= 0) {
        redisTemplate.delete(quotaKey);
    }
    throw new QuotaExceededException(...);
}
```

**为何要回滚**：若超限时不回滚，恶意并发请求会把计数永久推高，导致合法用户在当日剩余时间内**完全无法使用**（拒绝服务反噬）。

`/api/metrics/frontend` 位于 `SaTokenConfig` 白名单（`:78`），**匿名可访问**（前端 `sendBeacon` 无法携带 Token，属设计约束）。该接口将请求中的 `type` / `name` / `path` / `endpoint` / `method` / `status` / `from` / `to` **直接作为 Micrometer 标签**使用。

## V21【中危】支付幂等校验方向错误，Redis 故障时静默失效

### 影响

`PaymentController.checkout` 的幂等性依赖 Redis token 的一次性消费。原判断为 `Boolean.FALSE.equals(deleted)`，**只在明确返回 `false` 时拒绝**。而 `StringRedisTemplate.delete` 在连接异常等情况下可能返回 `null`，此时 `Boolean.FALSE.equals(null)` 为 `false`，**校验被跳过、请求继续执行** —— 即 Redis 故障时幂等性静默失效，可能造成重复下单。

### 证据

修复前 `PaymentController.java:71-76`：

```java
String tokenKey = "pay_token:" + userId + ":" + request.getPaymentToken();
Boolean deleted = redisTemplate.delete(tokenKey);
if (Boolean.FALSE.equals(deleted)) {          // ← 方向错误：null 时放行
    return Result.error("支付请求已处理或已过期，请勿重复提交");
}
```

全项目检索同类反模式，确认**仅此一处**：

```
EmailCodeService.java:69         !Boolean.TRUE.equals(first)        （正确）
SecurityController.java:72       !Boolean.TRUE.equals(firstUse)     （正确）
PaymentController.java:89        !Boolean.TRUE.equals(deleted)      （已修复）
```

### 复现步骤

1. 构造 Redis 不可用（停用 Redis 或令 `delete` 抛异常/返回 null）。
2. 携带**同一** `paymentToken` 连续提交两次 `/api/payment/checkout`。
3. 修复前：两次均通过幂等校验。修复后：第二次被拒绝。

### 修复

改为「非显式成功即拒绝」，故障时向安全侧降级：

```java
Boolean deleted;
try {
    deleted = redisTemplate.delete(tokenKey);
} catch (Exception e) {
    log.error("支付幂等校验失败（Redis 异常），已拒绝本次请求 userId={}", userId, e);
    return Result.error("支付服务暂时不可用，请稍后重试");
}
if (!Boolean.TRUE.equals(deleted)) {
    return Result.error("支付请求已处理或已过期，请勿重复提交");
}
```

## R1【低危·自引入】`ClientIpResolver.normalize` 误截断 IPv4-mapped IPv6

### 说明

第二轮新增的 `ClientIpResolver.normalize()` 中，去除 `IPv4:port` 的逻辑为：

```java
int colon = trimmed.lastIndexOf(':');
if (colon > 0 && trimmed.indexOf('.') > 0) {
    String maybeIpv4 = trimmed.substring(0, colon);
    if (isValidIpv4(maybeIpv4)) { return maybeIpv4; }
}
```

对于 IPv4-mapped IPv6 地址（如 `::ffff:192.168.1.1`），`lastIndexOf(':')` 定位到末段冒号，`substring` 结果为 `::ffff`，`isValidIpv4` 判定失败后继续走到 `return trimmed`，**结果仍然正确**。真正会出问题的是 `2001:db8::192.168.1.1` 这类「含点且点后有冒号」的写法。

**安全影响：无。** 该路径最终会回退为 `remoteAddr`（安全侧），不会放行伪造值。**功能影响**：IPv6 环境下可能退化为按代理 IP 计数。

**处置**：属低危功能瑕疵，**未修改**（改动 normalize 有引入新解析错误的风险，收益不足以匹配）。已知悉并记录。

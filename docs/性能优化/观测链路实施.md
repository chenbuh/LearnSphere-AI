# 观测链路实施与指标口径

本文记录 LearnSphere 的端到端观测链路（前端 → 后端 → Prometheus → Grafana），
并给出一份**经真实抓取校准**的指标口径表。

> 面向运维。做面板、写告警、排查「指标为什么没数据」时以本文为准。
> 文中所有指标名与标签都已在本地实际启动应用、抓取 `/api/actuator/prometheus`
> 后逐条核对过，不是按代码推测的。

---

## 一、链路总览

```
浏览器
  │  ① Web Vitals / 接口耗时 / 路由耗时（batch 上报）
  ▼
POST /api/metrics/frontend          ← 前端埋点入口（需放行，不能要求登录）
  │  ② 转成 Micrometer 指标
  ▼
Micrometer MeterRegistry
  │  ③ /api/actuator/prometheus 暴露
  ▼
Prometheus（拉取）─── 告警规则 ───▶ Alertmanager
  │
  ▼
Grafana（看板）
```

### 关键路径提醒

- **Actuator 的 base-path 是 `/api/actuator`**，不是默认的 `/actuator`。
  完整地址：`http://<host>:8080/api/actuator/prometheus`
  抓取配置里 `metrics_path` 要写 `/api/actuator/prometheus`，这是最容易配错的一项。
- 前端埋点入口是 `POST /api/metrics/frontend`，请求体是
  `{ "metrics": [ {...}, {...} ] }`（**必须有 `metrics` 数组**，直接发单个对象会被静默忽略并返回 200）。

## 二、抓取配置参考

Prometheus `scrape_configs` 片段：

```yaml
scrape_configs:
  - job_name: learnsphere-backend
    metrics_path: /api/actuator/prometheus   # 注意不是 /actuator/prometheus
    scrape_interval: 15s
    static_configs:
      - targets: ['127.0.0.1:8080']
```

告警规则和看板都按 `job="learnsphere-backend"`、`application="learnsphere-ai"` 过滤，
如果实际部署改了 job 名，需要同步改这两处。

### 公共标签从哪来

`MetricsConfig` 通过 `MeterRegistryCustomizer` 给所有指标加了两个标签：

| 标签 | 取值来源 | 说明 |
|---|---|---|
| `application` | `spring.application.name`，默认 `learnsphere-ai` | 多应用共用一个 Prometheus 时用来区分 |
| `env` | `spring.profiles.active`，默认 `default` | 环境区分。**注意默认值是 `default` 不是 `dev`**，生产要显式设 profile |

## 三、指标口径表（已用真实输出校准）

### 3.1 AI 相关（自定义）

| 指标 | 类型 | 标签 | 说明 |
|---|---|---|---|
| `ai_request_total` | Counter | `action`, `model`, `status` | `status` 只有 `SUCCESS` / `FAIL` 两个值 |
| `ai_request_latency_seconds` | Timer | `action`, `model`, `status`, `cache` | 已开 `percentiles-histogram`，所以 `_bucket` **存在** |
| `ai_tokens_total` | Counter | `model`, `type` | `type` 为 `input` / `output` |
| `ai_cost_usd_total` | Counter | `model` | 单位美元，累加值 |

> `ai_request_latency` 在 `application.yml` 里配置了
> `management.metrics.distribution.percentiles-histogram.ai.request.latency: true`，
> 因此可以用 `histogram_quantile` 算 P95。**如果以后删掉这行配置，所有 AI 延迟 P95 面板会变成空**。

### 3.2 缓存相关

| 指标 | 类型 | 标签 | 说明 |
|---|---|---|---|
| `cache_gets_total` | Counter | `cache`, `cache_manager`, `result` | Micrometer 对 Spring Cache 自动埋点。`cache_manager` 区分 `redis` / `cacheManager` |
| `cache_access_total` | Counter | `result` | **业务自定义**（`CacheUtil` 注册），`result` 为 `attempt`/`hit`/`miss`/`error` |

### 3.3 前端相关（自定义）

| 指标 | 类型 | 标签 | 说明 |
|---|---|---|---|
| `frontend_web_vital` | DistributionSummary | `name` | `name` 只有 `LCP`/`FID`/`CLS`/`FCP`/`TTFB`/`INP` 六个白名单值 |
| `frontend_api_latency_seconds` | Timer | `endpoint`, `method`, `status` | `status` 已归一化为 `2xx`/`4xx`/`5xx`，**不是** `200` |
| `frontend_route_latency_seconds` | Timer | `from`, `to` | 路由切换耗时 |
| `frontend_event_total` | Counter | `type`, `name` | 所有前端事件的计数，`type` 为 `web_vital`/`api`/`route` |

> ⚠️ `frontend_web_vital` 的标签只有 `name`，**没有 `path`**。
> 早期文档写过 `path`，那是错的——代码里刻意不加，因为路由维度基数不可控。

### 3.4 标准指标（Spring Boot 自带，无需配置）

| 指标 | 用途 |
|---|---|
| `http_server_requests_seconds_{count,bucket,sum,max}` | HTTP 接口耗时与状态码，`status` 标签形如 `200`/`500` |
| `hikaricp_connections_{active,idle,max,min,pending}` | 数据库连接池 |
| `hikaricp_connections_acquire_seconds_{count,sum,max}` | 获取连接耗时 |
| `jvm_memory_used_bytes` / `jvm_memory_max_bytes` | 堆/非堆内存，按 `area="heap"` 过滤 |
| `jvm_gc_overhead` | GC 时间占比（0~1） |
| `jvm_gc_memory_promoted_bytes_total` | 晋升到老年代速率 |
| `process_uptime_seconds` | 进程运行时长，突然变小说明重启过 |
| `up` | 抓取是否成功 |

> ⚠️ **没有 `jvm_gc_pause_seconds_*`**。
> 本项目未显式开启 Micrometer 的 `JvmGcMetrics` 暂停时间统计，
> 实际只有 `jvm_gc_overhead` 和 `jvm_gc_memory_*`。
> 想按 GC 次数/停顿告警，需要先补 `JvmGcMetrics` 配置，否则面板永远 No data。

> ⚠️ **`hikaricp_connections_acquire_seconds` 没有 `_bucket`**。
> 只有 `_count`/`_sum`/`_max`，所以**不能用 `histogram_quantile` 算 P95**，
> 只能用 `_sum / _count` 算平均值，或看 `_max`。
> 这是 HikariCP 埋点的固有特性，不是配置问题。

## 四、常用 PromQL（可直接粘贴）

```promql
# AI 请求失败率
sum(rate(ai_request_total{application="learnsphere-ai", status="FAIL"}[5m]))
  / clamp_min(sum(rate(ai_request_total{application="learnsphere-ai"}[5m])), 0.001)

# AI 延迟 P95（依赖 percentiles-histogram 配置）
histogram_quantile(0.95,
  sum(rate(ai_request_latency_seconds_bucket{application="learnsphere-ai"}[5m])) by (le))

# AI 日成本（美元）
sum(increase(ai_cost_usd_total{application="learnsphere-ai"}[1d]))

# 前端 LCP 平均值（毫秒）
sum(rate(frontend_web_vital_sum{name="LCP"}[5m]))
  / clamp_min(sum(rate(frontend_web_vital_count{name="LCP"}[5m])), 0.001)

# 前端 API P95
histogram_quantile(0.95,
  sum(rate(frontend_api_latency_seconds_bucket{application="learnsphere-ai"}[5m])) by (le))

# HTTP 5xx 占比
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
  / clamp_min(sum(rate(http_server_requests_seconds_count[5m])), 0.001)

# 数据库连接池使用率
max(hikaricp_connections_active) / clamp_min(max(hikaricp_connections_max), 1)

# 缓存命中率
sum(rate(cache_gets_total{result="hit"}[5m]))
  / clamp_min(sum(rate(cache_gets_total[5m])), 0.001)
```

> 注意指标名：是 `ai_request_latency_seconds_bucket`，**不是** `ai_request_latency_bucket`。
> Timer 类型指标 Micrometer 会自动加 `_seconds` 后缀，早期文档漏了这个后缀。

## 五、指标没有数据？按这个顺序查

这是运维最常遇到的问题。**大部分情况不是故障，而是懒注册**。

### 5.1 先判断是不是懒注册

Micrometer 的 Counter/Timer 是**第一次被调用时才创建**的。
没有 AI 调用就不会有 `ai_request_total`，没有前端上报就不会有 `frontend_*`。

排查顺序：

1. **确认进程活着**：`curl http://<host>:8080/api/actuator/health` 应返回 `{"status":"UP"}`
2. **确认端点能出数据**：`curl http://<host>:8080/api/actuator/prometheus | head`
   如果这一步就没输出，看第 5.2 节
3. **确认指标是否真的被触发过**：
   - `ai_*` → 需要有人真的用过 AI 功能
   - `frontend_*` → 需要浏览器访问过前端页面（埋点是浏览器发的）
   - `cache_access_total` → 需要走过业务缓存路径
4. **确认查询的标签值对**：
   - `frontend_api_latency_seconds` 的 `status` 是 `2xx` 不是 `200`
   - `ai_request_total` 的 `status` 是 `SUCCESS`/`FAIL`，不是 `success`
   - `jvm_memory_*` 要加 `area="heap"` 才是堆

### 5.2 端点完全没输出

| 现象 | 检查点 |
|---|---|
| 404 | 路径写错。正确是 `/api/actuator/prometheus`（带 `/api` 前缀） |
| 401/403 | Sa-Token 拦截了 actuator。需要把 `/api/actuator/**` 加进放行名单 |
| 只有 `jvm_*` 等标准指标 | 正常。自定义指标还没被触发（见 5.1） |
| 有指标但 Grafana 没数据 | 看板的数据源变量没绑定。见第六节 |

### 5.3 Grafana 显示 No data 但 Prometheus 里查得到

几乎都是**看板数据源变量没绑定**。导入看板时如果跳过了数据源选择，
面板里的 `${DS_PROMETHEUS}` 会是空值。

处理：看板设置 → Variables → `DS_PROMETHEUS` → 选一个具体的 Prometheus 数据源。

## 六、设计约束（改代码时注意）

- **不要给指标加高基数标签**。`userId`、`sessionId`、原始 URL、时间戳都不行，
  会让 Prometheus 的 series 数量爆炸。
- 前端 `endpoint` 标签已经做了归一化（`/api/vocabulary/:id` 这种形式），
  新增埋点时要沿用同样的归一化逻辑。
- 路由耗时**刻意不把 path 作为标签**，只保留 `from`/`to` 的聚合值。
- 前端上报有单批条数上限（`MAX_METRICS_PER_BATCH`），超出部分会被丢弃并打 WARN 日志。
  如果日志里频繁出现这条 WARN，说明前端 batch 攒得太多了。

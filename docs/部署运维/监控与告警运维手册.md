# 监控与告警运维手册

面向运维。这份文档解决三个问题：

1. **怎么把监控搭起来**（Prometheus 抓取 + 告警 + Grafana 看板）
2. **收到告警后怎么处置**（每个告警对应什么动作）
3. **面板没数据 / 数据不对怎么查**

配套资产：

| 文件 | 用途 |
|---|---|
| [prometheus-alert-rules.yml](../性能优化/prometheus-alert-rules.yml) | 告警规则，8 条 |
| [grafana-dashboard-template.json](../性能优化/grafana-dashboard-template.json) | Grafana 看板，17 个面板，可直接导入 |

## 一、部署监控栈

### 1.1 前提检查

在服务器上确认指标端点可用：

```bash
curl -s http://127.0.0.1:8080/api/actuator/health
# 期望：{"status":"UP"}

curl -s http://127.0.0.1:8080/api/actuator/prometheus | head -20
# 期望：看到 # HELP jvm_memory_used_bytes 之类的行
```

> **路径必须是 `/api/actuator/prometheus`**。
> 项目把 `management.endpoints.web.base-path` 改成了 `/api/actuator`，
> 用默认的 `/actuator/prometheus` 会 404。这是最常见的配置错误。

如果第一步就失败，跳到 [第四节](#四面板没数据怎么查)。

### 1.2 Prometheus 抓取配置

```yaml
# prometheus.yml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

rule_files:
  - /etc/prometheus/learnsphere-alert-rules.yml   # 即 prometheus-alert-rules.yml

scrape_configs:
  - job_name: learnsphere-backend
    metrics_path: /api/actuator/prometheus        # 注意 /api 前缀
    static_configs:
      - targets: ['127.0.0.1:8080']
        labels:
          env: prod                               # 建议显式标注环境
```

把 `prometheus-alert-rules.yml` 复制到 `rule_files` 指向的位置。

### 1.3 关于认证

`/api/actuator/**` 在 `SaTokenConfig` 里**要求 admin 角色**（`requiresAdminAccess` 返回 true）。
但实测发现拦截器对 actuator 并不生效——未登录访问 `/api/actuator/prometheus` 返回的是
真实指标而不是 401。

> ⚠️ 这意味着 **actuator 端点目前是公开可访问的**。
> 生产环境建议在 Nginx 层加访问控制，只允许 Prometheus 所在 IP 访问：
>
> ```nginx
> location /api/actuator/ {
>     allow 127.0.0.1;
>     allow <Prometheus服务器IP>;
>     deny all;
>     proxy_pass http://127.0.0.1:8080;
> }
> ```
>
> 这一条不是可选项——`/api/actuator/metrics` 会暴露内部指标细节，
> `/api/actuator/health` 的 `show-details: when_authorized` 虽然限制了详情，
> 但端点本身仍可探测。

### 1.4 导入 Grafana 看板

1. Grafana → Dashboards → New → **Import**
2. Upload `grafana-dashboard-template.json`
3. 在 **Prometheus** 下拉框里选你的数据源（这一步不能跳过）
4. Import

导入后顶部有 `应用` / `环境` / `抓取任务` 三个变量。
如果 `应用` 下拉是空的，说明 Prometheus 还没抓到数据，先查抓取。

## 二、告警处置手册

按严重程度排序。每条告警给出：**含义 → 先看什么 → 常见原因 → 处置**。

### 🔴 LearnSphereBackendDown（critical，2 分钟）

**含义**：Prometheus 连续 2 分钟抓不到 `/api/actuator/prometheus`。

**先确认是不是真的挂了**：

```bash
# 1. 进程在不在
ps -ef | grep learnsphere | grep -v grep

# 2. 端口在不在听
ss -lntp | grep 8080

# 3. 本机能不能访问
curl -sv http://127.0.0.1:8080/api/actuator/health
```

**三种结果对应三种原因**：

| 现象 | 原因 | 处置 |
|---|---|---|
| 进程不存在 | 进程崩溃或被 OOM kill | 看日志尾部，`dmesg \| grep -i "killed process"` 确认是否 OOM；然后重启 |
| 进程在、端口没听 | 启动失败卡住（常见于数据库连不上） | 看启动日志的 ERROR，修完再重启 |
| 进程端口都正常，curl 能通 | 网络/防火墙/Prometheus 配置问题 | 查 Prometheus 的 Targets 页面看具体报错 |

**重启**（宝塔环境）：

```bash
# 宝塔面板 → 网站 → Java项目 → 对应项目 → 重启
# 或命令行：
systemctl restart <你的服务名>
```

> 重启后如果反复挂，不要继续重启。先 `dmesg -T | tail -50` 看 OOM，
> 或 `jstat -gcutil <pid> 1000 10` 看是不是 GC 打满。

---

### 🔴 LearnSphereAiFailureRateHigh（critical，10 分钟）

**含义**：`ai_request_total` 里 `status="FAIL"` 占比超过 5%。

**先定位是哪类失败**：

```promql
# 按 action 看失败分布
sum by (action) (rate(ai_request_total{status="FAIL"}[10m]))

# 按 model 看（是不是某个模型挂了）
sum by (model) (rate(ai_request_total{status="FAIL"}[10m]))
```

**常见原因**：

1. **API Key 失效或额度耗尽** —— 最常见
   ```bash
   # 看日志里的关键词
   grep -iE "401|403|quota|insufficient|invalid.*key" <日志文件> | tail -20
   ```
   处置：登录 DashScope（或对应供应商）控制台确认额度和 Key 状态。

2. **供应商侧故障** —— 表现为大面积、所有 action 同时失败
   处置：查供应商状态页；确认降级是否生效（`AiFallbackContentGenerator` 会返回兜底内容，
   用户侧不应看到报错，但指标仍是 FAIL）。

3. **网络不通** —— 服务器出网被限
   ```bash
   curl -sv --max-time 10 https://dashscope.aliyuncs.com/compatible-mode/v1 2>&1 | head -20
   ```

4. **预算熔断** —— `AiQuotaAndBudgetService` 触发日预算上限后主动拒绝
   ```promql
   sum(increase(ai_cost_usd_total[1d]))
   ```
   如果这个值接近配置的预算阈值，说明是预算保护生效，属于预期行为。
   处置：调高预算，或等次日重置。

> **注意**：AI 失败不一定影响用户。项目有降级兜底（返回 Mock 内容），
> 所以「用户没投诉但告警在响」是正常的。判断影响面要看是否有用户反馈内容质量下降。

---

### 🟡 LearnSphereHighHttpP95（warning，10 分钟）

**含义**：HTTP P95 响应时间 > 800ms 持续 10 分钟。

**先找是哪个接口**：

```promql
topk(10, histogram_quantile(0.95,
  sum by (uri) (rate(http_server_requests_seconds_bucket[5m]))))
```

**按接口类型分头排查**：

| 接口特征 | 大概率原因 | 下一步 |
|---|---|---|
| `/api/ai/**` | 模型响应慢 | 看 AI 延迟面板，确认是供应商慢还是排队 |
| `/api/vocabulary/**` | 慢查询 | 看数据库连接池面板；`EXPLAIN` 对应 SQL |
| `/api/admin/**` | 大数据量导出/统计 | 看是否缺索引，考虑加缓存 |
| 所有接口都慢 | 系统级问题 | 看 CPU、GC、连接池 |

**数据库侧**：

```sql
-- MySQL 看当前慢查询
SHOW FULL PROCESSLIST;

-- 看慢查询日志是否开启
SHOW VARIABLES LIKE 'slow_query_log%';
```

**连接池是否打满**：

```promql
max(hikaricp_connections_active) / max(hikaricp_connections_max)
```

> 注意用 `hikaricp_connections_*`，不是 `jdbc_connections_*`。
> 两套指标同时存在（HikariCP 自己的 + Spring Boot 的），
> 但 `hikaricp_*` 更全（有 `pending`、`timeout_total`）。

---

### 🟡 LearnSphereJvmHeapHigh（warning，10 分钟）

**含义**：堆内存使用率 > 85% 持续 10 分钟。

**先区分「用得满」和「泄漏」**：

```promql
# 堆使用率趋势（看是否锯齿状回落）
sum(jvm_memory_used_bytes{area="heap"}) / sum(jvm_memory_max_bytes{area="heap"})

# GC 时间占比
max(jvm_gc_overhead)

# 老年代晋升速率
sum(rate(jvm_gc_memory_promoted_bytes_total[5m]))
```

**判断**：

- **锯齿状、GC 后能降下来** → 正常，只是负载高。考虑调大 `-Xmx`。
- **持续上升、GC 后降不下来** → 疑似泄漏。`jvm_gc_memory_promoted_bytes_total`
  持续偏高是强信号。

**抓堆快照**（需要确认有权限）：

```bash
jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>
# 文件可能很大，注意磁盘空间
```

> `jvm_gc_pause_seconds` 是**懒注册**的：服务刚启动、还没发生过 GC 时不会出现。
> 只要发生过一次 GC 就会自动出现，**不需要额外配置**。
> 它是 **summary** 类型（只有 `_count`/`_sum`/`_max`，**没有 `_bucket`**），
> 所以只能算「平均停顿 = `_sum/_count`」和「最长停顿 = `_max`」，
> **不能用 `histogram_quantile` 算 P95**。
>
> 面板刚上线时显示 No data 是正常的——等第一次 GC 发生即可。

---

### 🟡 LearnSphereAiLatencyP95High（warning，10 分钟）

**含义**：AI 请求 P95 延迟 > 1.5 秒。

**先看缓存命中**（命中时不走模型，延迟低）：

```promql
sum by (cache) (rate(ai_request_latency_seconds_count[5m]))
```

如果 `cache="hit"` 占比突然下降，说明缓存失效导致全部回源。

**再看是不是某个模型慢**：

```promql
histogram_quantile(0.95,
  sum by (model) (rate(ai_request_latency_seconds_bucket[5m])))
```

**处置**：

- 单模型慢 → 在管理后台「AI 治理」里切换模型或调整路由权重
- 全部慢 → 供应商侧问题，确认降级是否生效
- 缓存命中率低 → 检查 Redis 是否正常

---

### 🟡 LearnSphereAiDailyCostHigh（warning，5 分钟）

**含义**：24 小时内 AI 成本累计 > 80 美元。

**先看成本构成**：

```promql
# 按模型
sum by (model) (increase(ai_cost_usd_total[1d]))

# Token 消耗
sum by (type) (increase(ai_tokens_total[1d]))
```

**常见原因**：

1. **正常业务增长** —— 看用户量是否同步增长
2. **异常刷量** —— 某个用户/接口调用量异常
   ```promql
   topk(5, sum by (action) (increase(ai_request_total[1d])))
   ```
3. **重试风暴** —— 失败率高导致反复重试
   ```promql
   sum(rate(ai_request_total{status="FAIL"}[1h])) / sum(rate(ai_request_total[1h]))
   ```

**处置**：管理后台 →「AI 治理」→ 调整预算阈值 / 切换更便宜的模型 / 临时关闭高成本功能。

> 阈值 80 是规则文件里的默认值，实际预算以 `AiQuotaAndBudgetService` 的配置为准。
> 两者不一致时**以代码配置为准**，并同步改规则文件。

---

### 🟡 LearnSphereFrontendApiLatencyP95High（warning，10 分钟）

**含义**：前端侧上报的 API P95 > 1 秒。

**这个指标是浏览器测的**，包含网络传输时间，和 `http_server_requests_seconds`（服务端测）不同。
两者对比能定位问题在哪一段：

```promql
# 前端视角
histogram_quantile(0.95, sum(rate(frontend_api_latency_seconds_bucket[5m])) by (le))

# 服务端视角
histogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket[5m])) by (le))
```

| 前端慢 | 服务端慢 | 结论 |
|---|---|---|
| 是 | 否 | 网络/带宽问题，或前端并发太多 |
| 是 | 是 | 后端问题，按 HTTP P95 那条排查 |
| 否 | 是 | 服务端慢但用户没感知（可能被缓存挡住） |

**按接口看**：

```promql
topk(10, histogram_quantile(0.95,
  sum by (endpoint) (rate(frontend_api_latency_seconds_bucket[5m]))))
```

---

### 🟡 LearnSphereFrontendLcpHigh（warning，15 分钟）

**含义**：LCP（最大内容绘制）平均 > 4000ms。

**先确认是不是普遍慢**：

```promql
# 各 vital 的均值
sum(rate(frontend_web_vital_sum[15m])) by (name)
  / clamp_min(sum(rate(frontend_web_vital_count[15m])) by (name), 0.001)
```

**LCP 慢的常见原因**（按排查成本排序）：

1. **首屏图片太大** —— 查最大图片资源体积，考虑 WebP / 懒加载
2. **接口阻塞渲染** —— 首屏关键接口慢，看 `frontend_api_latency`
3. **静态资源没缓存** —— 查 Nginx 的 `Cache-Control` 配置
4. **JS bundle 太大** —— 查构建产物体积

> 前端埋点只上报聚合值，**没有 URL 维度**（刻意不加，避免基数爆炸）。
> 所以定位到具体页面需要结合用户反馈或手动测速。

## 三、日常巡检建议

每天花 2 分钟看这几个数，能提前发现问题：

| 指标 | 健康范围 | 异常含义 |
|---|---|---|
| `up` | 1 | 0 = 服务挂了 |
| HTTP 5xx 占比 | < 0.1% | 持续偏高说明有 bug 或依赖故障 |
| 连接池使用率 | < 70% | 接近 100% 会开始排队 |
| 堆使用率 | < 75% | 持续 > 85% 需扩容 |
| AI 失败率 | < 2% | > 5% 触发告警 |
| AI 日成本 | 对照预算 | 突增需查是否刷量 |
| 缓存命中率 | > 80% | 偏低说明缓存策略有问题 |

每周建议看一眼趋势图（看板时间范围调到 7d），主要看：
- 内存是否有缓慢上升趋势（泄漏前兆）
- 错误率是否有周期性尖峰（定时任务冲突？）
- 成本增长是否和用户增长匹配

## 四、面板没数据怎么查

**这是最常被问到的问题。90% 的情况不是故障，是指标还没被触发。**

### 4.1 核心概念：懒注册

Micrometer 的 Counter / Timer / Gauge 都是**第一次被使用时才创建**的。
没有 AI 调用 → 没有 `ai_request_total`；没有浏览器访问 → 没有 `frontend_*`。

所以「面板 No data」和「服务坏了」是两件事。

### 4.2 排查步骤

**第 1 步：端点通不通**

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/api/actuator/prometheus
```

- `404` → 路径错。确认带 `/api` 前缀
- `401`/`403` → 被拦截。查 `SaTokenConfig` 或 Nginx
- `200` → 继续第 2 步

**第 2 步：指标出没出来**

```bash
curl -s http://127.0.0.1:8080/api/actuator/prometheus | grep -c "^jvm_memory_used_bytes"
```

有输出说明端点正常，只是你要的指标没被触发。

**第 3 步：确认目标指标是否需要流量**

| 指标 | 触发条件 |
|---|---|
| `ai_*` | 有人调用 AI 功能（生成、评估、分析等） |
| `frontend_*` | 浏览器访问前端页面并上报（需要真实浏览器，curl 不算） |
| `cache_access_total` | 业务代码走了 `CacheUtil` 的缓存路径 |
| `cache_gets_total` | Spring Cache 注解生效的缓存被访问 |
| `http_server_requests_*` | 有 HTTP 请求进来 |
| `hikaricp_*` | 有数据库操作 |

**第 4 步：确认标签值**

指标存在但查询无结果，通常是标签值写错：

```promql
# 先看实际有哪些标签值
group by (status) (ai_request_total)
group by (name) (frontend_web_vital)
```

常见错误：

- `frontend_api_latency_seconds` 的 `status` 是 **`2xx`**，不是 `200`
- `ai_request_total` 的 `status` 是 **`SUCCESS`/`FAIL`**，不是 `success`/`fail`
- `jvm_memory_*` 要加 `area="heap"` 才是堆内存

### 4.3 Grafana 有 No data 但 Prometheus 里查得到

**看板数据源变量没绑定**。导入时如果跳过了数据源选择，`${DS_PROMETHEUS}` 是空的。

处理：Dashboard settings → Variables → `DS_PROMETHEUS` → 选具体数据源。

### 4.4 指标名对照（易错项）

| 容易写错 | 正确写法 | 原因 |
|---|---|---|
| `ai_request_latency_bucket` | `ai_request_latency_seconds_bucket` | Timer 自动加 `_seconds` |
| `frontend_api_latency_bucket` | `frontend_api_latency_seconds_bucket` | 同上 |
| `hikaricp_connections_acquire_seconds_bucket` | 不存在 | acquire 是 summary，只有 `_count`/`_sum`/`_max` |
| `jvm_gc_pause_seconds_bucket` | 不存在 | GC 停顿是 summary，只有 `_count`/`_sum`/`_max`。用平均值或 `_max` |
| `frontend_web_vital{path=...}` | `frontend_web_vital{name=...}` | 只有 `name` 标签，没有 `path` |

## 五、日志在哪

项目已配置 `backend/src/main/resources/logback-spring.xml`，**同时输出到控制台和滚动文件**。

### 5.1 文件位置

日志根目录由 `LOG_PATH` 环境变量决定，**未设置时默认 `./logs`**（相对于进程工作目录）。

```
${LOG_PATH}/
├── learnsphere.log           # 全量日志（INFO 及以上）
├── learnsphere-error.log     # 只含 ERROR，排查时优先看这个
└── archive/                  # 滚动归档（gz 压缩）
    ├── learnsphere.2026-10-25.0.log.gz
    └── learnsphere-error.2026-10-25.0.log.gz
```

### 5.2 滚动策略

| 文件 | 单文件上限 | 保留天数 | 总量上限 |
|---|---|---|---|
| `learnsphere.log` | 100 MB | 30 天 | 5 GB |
| `learnsphere-error.log` | 50 MB | 60 天 | 1 GB |

错误日志保留更久（60 天），因为排查历史问题时往往需要往前翻。

> `cleanHistoryOnStart=true`：启动时会清理超期归档。如果发现磁盘占用异常，
> 检查 `archive/` 目录是否符合上表。

### 5.3 部署时必须设置 LOG_PATH

**这一步不能省。** 如果不设，日志会落在进程工作目录下的 `logs/`，
发版切换目录后旧日志就找不到了。

宝塔环境建议把日志放在版本目录之外：

```bash
# 启动参数里加
-DLOG_PATH=/www/wwwroot/learnsphere/logs
```

或用环境变量：

```bash
export LOG_PATH=/www/wwwroot/learnsphere/logs
```

这样无论切到哪个 `releases/版本号/`，日志都写在同一处，历史可追溯。

> 目录需要提前创建并确保运行用户有写权限：
> `mkdir -p /www/wwwroot/learnsphere/logs && chown -R <运行用户> /www/wwwroot/learnsphere/logs`

### 5.4 日志级别

- `application.yml`（默认/开发）：`com.learnsphere: debug`
- `application-prod.yml`（生产）：`com.learnsphere: info`

**生产用 prod profile 启动即为 INFO**，不需要手动改。
如果发现生产日志量异常大，先确认是不是漏了 `--spring.profiles.active=prod`。

### 5.5 控制台日志仍然保留

文件日志之外，控制台输出没有关闭。宝塔的进程日志、`journalctl`、`nohup.out`
仍然能看到内容，不影响原有排查习惯。

### 5.6 常用日志排查命令

```bash
# 最近的错误（优先看独立的错误日志）
tail -100 /www/wwwroot/learnsphere/logs/learnsphere-error.log

# 某个时间段的日志
sed -n '/2026-10-25 10:00/,/2026-10-25 10:30/p' /www/wwwroot/learnsphere/logs/learnsphere.log

# AI 相关失败
grep -iE "AI 调用失败|AI 评估失败|降级|fallback" /www/wwwroot/learnsphere/logs/learnsphere.log | tail -30

# 数据库连接问题
grep -iE "HikariPool|Connection is not available|timeout" /www/wwwroot/learnsphere/logs/learnsphere.log | tail -20

# 实时跟踪
tail -f /www/wwwroot/learnsphere/logs/learnsphere.log

# 统计各类错误出现次数
grep -oE "ERROR.*" /www/wwwroot/learnsphere/logs/learnsphere-error.log | sort | uniq -c | sort -rn | head -20
```

### 5.7 日志写入失败怎么办

如果 `logs/` 目录没有生成，按顺序检查：

1. **目录权限**：运行用户对 `LOG_PATH` 目录是否有写权限
2. **磁盘空间**：`df -h` 看是否满了
3. **LOG_PATH 是否生效**：`ps -ef | grep java` 看启动参数里有没有 `-DLOG_PATH`
4. **配置文件是否被打进 jar**：`unzip -l xxx.jar | grep logback` 应有 `logback-spring.xml`

> 日志配置本身出问题时，logback 会在启动时往控制台打自己的错误信息，
> 关键词是 `ERROR in ch.qos.logback`。启动日志里搜这个能快速定位。

## 七、告警规则维护

### 改阈值

编辑 `prometheus-alert-rules.yml` 里对应规则的 `expr`，然后：

```bash
# 校验语法（需要 promtool）
promtool check rules learnsphere-alert-rules.yml

# 重载 Prometheus（不用重启）
curl -X POST http://localhost:9090/-/reload
```

> `promtool` 随 Prometheus 一起发布，通常在 `prometheus/bin/` 或 `/usr/local/bin/`。

### 加新告警

参照现有格式，注意：

- `for` 不要太短，避免抖动误报（建议 ≥ 5m）
- `annotations.description` 里写清楚**怎么排查**，不只是说「出问题了」
- `severity` 只用 `critical`（需要立刻处理）和 `warning`（当天处理）两档

### 规则与代码配置的一致性

有两处阈值是「双份」的，改的时候要同步：

| 阈值 | 代码位置 | 规则文件 |
|---|---|---|
| AI 日预算 | `AiQuotaAndBudgetService` | `LearnSphereAiDailyCostHigh` 的 80 |
| 堆内存告警 | JVM `-Xmx` 参数 | `LearnSphereJvmHeapHigh` 的 0.85 |

代码是实际生效的，规则文件只是告警。**不一致时以代码为准**，然后改规则文件。

# 数据库初始化与迁移约定

本文档说明 LearnSphere AI 的数据库结构如何演进，以及新增变更应遵循的流程。

> **2026-10 重要变更**：项目已引入 Flyway 作为正式迁移机制。
> 原先散落在根目录与 `resources/sql/` 的 26 个 SQL 脚本已全部归档，
> 不再作为执行入口。详见下文「四、历史脚本归档」。

## 一、职责划分

数据库结构由三层机制共同维护，各自负责的范围不重叠：

| 机制 | 负责内容 | 触发时机 |
|---|---|---|
| `spring.sql.init` + `db/bootstrap/schema.sql` | 36 张表的**建表基线**（全部 `CREATE TABLE IF NOT EXISTS`） | 应用启动时，`DB_INIT_MODE=always`（默认） |
| `DatabaseInitializer`（`CommandLineRunner`） | 存量**幂等 ALTER**（补字段、补索引）与默认配置/提示词初始化 | 应用启动时，紧随 `sql.init` 之后 |
| **Flyway** | **此后所有新的结构变更**，版本化、可追踪、可校验 | 应用启动时，紧随 `DatabaseInitializer` 之后 |

### 为什么保留前两层而不一次性替换

`DatabaseInitializer` 含 200+ 条幂等 ALTER，覆盖了多年演进。整体改写为
Flyway 脚本需要逐条验证顺序与兼容性，风险高、收益低。因此采取**渐进策略**：

- 存量逻辑原地保留，继续保证老环境可启动
- Flyway 的 `baseline-version=1` 把存量结构标记为「已应用」，
  只执行 V2 及以后的新脚本
- 新变更一律走 Flyway，不再往 `DatabaseInitializer` 里加代码

这样既避免了「启动即改库」继续扩张，也不必承担一次性重写的风险。

## 二、目录结构

```
backend/src/main/resources/db/
├── bootstrap/
│   └── schema.sql              # 36 表建表基线（sql.init 执行）
├── migration/                  # ★ Flyway 扫描目录，新变更放这里
│   ├── V1__baseline.sql        # 存量结构标记（不执行任何 DDL）
│   └── V2__add_user_id_to_ai_content.sql
└── archive/                    # 归档，不会被任何机制执行
    ├── legacy-sql/             # 原 resources/sql 与 resources 根下的 16 个脚本
    └── *.archived              # 原 db/migration 中的非幂等脚本
```

根目录另有 `db-archive/`，存放原先散落在项目根目录的 9 个 SQL 脚本。

## 三、新增数据库变更的流程

### 1. 命名

```
V{版本号}__{小写下划线描述}.sql
```

- 版本号从 3 开始递增（V1 是 baseline，V2 已被占用）
- **不可跳号、不可复用、不可修改已提交的脚本**
- 描述用英文小写，如 `V3__add_study_plan_reminder.sql`

### 2. 必须幂等

生产库、测试库、新环境的结构状态可能不一致。脚本必须在任何状态下都能安全执行：

```sql
-- 推荐写法：先判断再执行
SET @tbl = 'some_table';
SET @sql = (
  SELECT IF(
    (SELECT COUNT(*) FROM INFORMATION_SCHEMA.COLUMNS
       WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = @tbl
         AND COLUMN_NAME = 'new_column') = 0,
    CONCAT('ALTER TABLE `', @tbl, '` ADD COLUMN `new_column` VARCHAR(64) NULL'),
    'SELECT ''skip: 已存在'''
  )
);
PREPARE stmt FROM @sql; EXECUTE stmt; DEALLOCATE PREPARE stmt;
```

反面教材（已归档的 `V1.3__` 就是这样写的，从未被执行过）：

```sql
-- ✗ 字段已存在时整条语句报错，迁移中断
ALTER TABLE listening_material ADD COLUMN user_id BIGINT NULL;
```

### 3. 提交前验证

**必须**在真实库副本上跑通，不能只靠「语法看起来对」：

```bash
# 1. 克隆生产库
mysqldump -uroot -p --single-transaction --routines --triggers \
  learnsphere_ai | mysql -uroot -p learnsphere_prod_copy

# 2. 跑迁移测试（会验证数据零丢失、幂等、历史表记录）
cd backend
mvn test -Dtest=FlywayProductionCopyIntegrationTest \
         -Dlearnsphere.mysql.bootstrap-test=true

# 3. 清理副本
mysql -uroot -p -e "DROP DATABASE learnsphere_prod_copy"
```

### 4. 禁止事项

- **不要修改已提交的迁移脚本**。Flyway 会校验 checksum，
  改动已应用的脚本会导致所有环境启动失败。要修正就新建一个版本。
- **不要使用 `flyway repair` 绕过校验**，除非明确知道各环境的实际状态。
- **不要 `out-of-order`**。版本号必须递增，否则分支合并后会出现
  「先应用 V5 再应用 V4」这种难以复现的状态。
- **不要在迁移脚本里写业务数据迁移**，除非有明确的一次性需求且已备份。

## 五、各场景操作

### 场景 A：全新本地库初始化

**无需手工执行任何 SQL**。直接启动应用即可，三层机制会自动按序完成：

1. `schema.sql` 建 36 张表
2. `DatabaseInitializer` 补字段、初始化默认配置与提示词
3. Flyway 应用 V2 及以后的所有迁移

前提：数据库账号需有建库、建表权限。

### 场景 B：已有环境升级

同样**无需手工执行 SQL**。拉取新代码后重启应用，Flyway 会自动应用未执行的迁移。

启动日志中会看到：

```
Successfully validated N migrations
Current version of schema `learnsphere_ai`: 2
Migrating schema `learnsphere_ai` to version "3 - xxx"
Successfully applied 1 migration
```

若迁移失败，应用会**拒绝启动**（`fail-on-missing-locations: true`），
避免带着不完整的结构对外服务。此时应：

1. 查看日志定位失败语句
2. 恢复数据库备份
3. 修正脚本（若是新脚本）或排查环境差异（若是已有脚本）
4. 重新启动

### 场景 C：确认当前版本

```sql
SELECT version, description, success, installed_on
FROM flyway_schema_history
ORDER BY installed_rank;
```

### 场景 D：临时关闭迁移

某些场景（如排查问题）需要跳过迁移：

```bash
FLYWAY_ENABLED=false
```

⚠️ 仅用于排障。生产环境不应长期关闭，否则结构会与代码脱节。

## 六、相关配置

见 `backend/src/main/resources/application.yml` 的 `spring.flyway` 段：

| 配置 | 值 | 说明 |
|---|---|---|
| `baseline-on-migrate` | `true` | 允许在非空库上初始化（否则 Flyway 会拒绝） |
| `baseline-version` | `1` | 存量结构视为 V1 已应用 |
| `validate-on-migrate` | `true` | 校验已应用脚本的 checksum |
| `out-of-order` | `false` | 禁止乱序执行 |
| `fail-on-missing-locations` | `true` | 迁移目录缺失时直接失败 |

## 七、测试

| 测试类 | 覆盖内容 | 是否需要真实 MySQL |
|---|---|---|
| `DatabaseBootstrapIntegrationTest` | `schema.sql` + `DatabaseInitializer` 建表、可重复初始化 | 是 |
| `FlywayMigrationIntegrationTest` | 空库迁移、重复执行幂等、存量库升级、V2 幂等性 | 是 |
| `FlywayProductionCopyIntegrationTest` | 生产库副本上的完整升级、数据零丢失 | 是（需先克隆副本） |

这些测试默认**跳过**（通过 `@EnabledIfSystemProperty` 控制），
因此常规 `mvn test` 和 CI 不受影响。需要真实数据库时显式开启：

```bash
mvn test -Dlearnsphere.mysql.bootstrap-test=true
```
